## Problems Encountered

1. **Podwójne `search` w AI Assistant** (istniejący błąd): po Enter `SearchField` wywoływał handler dwa razy, co otwierało dwa `BusyDialog`. Referencja do pierwszego była nadpisywana, więc trwale blokował UI. Wykryte przez OPA i odtworzone w przeglądarce (`EnterText`). Naprawa: jedno zapytanie naraz (`_bAiQueryRunning`).
2. Istniejące: brak obsługi błędów `fetch` w AI i Scanner (otwarty `BusyDialog`), `ReferenceError` (`sResponse`, `reject`), błędy `Failed to read path` w dialogu skanera, `FormatException` pola waluty. Wszystkie poprawione (szczegóły w przewodniku, sekcje 7–8).
3. Test `__proto__` wykrył, że adapter AI traktował `__proto__` jako znane pole legacy. Naprawione przez `hasOwnProperty`.
4. Test wykrył, że `parseFloat("1; DROP…")` zwracał 1. Walidacja zmieniona na `Number()`.
5. Ograniczenia harnessu, nie aplikacji: panele są domyślnie zwinięte (OPA rozwija je przed wpisaniem), `OverflowToolbar` chowa przyciski (OPA wywołuje `firePress` dla nierenderowanych przycisków), `waitFor` na stronę przy otwartym dialogu.
6. Bazowy test OPA wymagał `id="page"`; dodano id do `Page`.
7. **`npm ci` u użytkownika: `EPERM unlink keyring.win32-x64-msvc.node`.** Przyczyna potwierdzona: zatrzymanie serwera `fiori run` uruchomionego przez agenta (zamknięcie powłoki) nie kończy na Windows drzewa procesów `npm → fiori → ui5 serve`. Proxy fiori-tools ładuje natywny moduł keyring (`@zowe/secrets-for-zowe-sdk`) i blokuje plik, a `npm ci` usunął resztę `node_modules` (brak `ui5`/`fiori`). Po zwolnieniu blokady ponowne `npm ci` + build + unit 44/44 + OPA 13/13 PASS. Przed `npm ci` zatrzymaj `serve-mock` (Ctrl+C w jego terminalu). Runner kończy się teraz od razu (kod 2) z instrukcją, gdy serwer na 8085 nie działa.

## Decisions Made

- Kokpit to mixin istniejącego kontrolera, nie nowa aplikacja ani nowy kontroler routingu. Logika jest w czystych, testowalnych modułach.
- Tabela KSeF działa na modelu JSON i filtrowaniu klienckim (mała liczba nagłówków). Paging serwerowy zostaje dla G-01.
- UI nie używa `CREATE KsefOperations` jako „Send”, bo klient podawałby `sapDocumentRef`, `taxpayerNip` i `idempotencyKey` bez weryfikacji z SAP. Wymagana jest dedykowana akcja (G-02).
- UI nie łączy się z RAP Web API (`odata_v4_webapi`) bezpośrednio: brak izolacji NIP w DCL i architektura UI → CAP (ADR-0001).
- Statusy spoza `NEW`/`ACCEPTED` są oznaczone jako oczekiwane; nieznany status blokuje akcje.
- Domyślny `dataMode: "mock"` z wyraźnym banerem, bo tryb `cap` nie ma jeszcze listy (G-01).
